Pythonの変数モデルについて整理する。

## 結論
Pythonの変数は「名前空間 (namespace) の中の束縛 (binding)」であり、C++のポインタとは別物。
言語仕様レベルで **名前空間** と **オブジェクト空間** の2層に分かれており、ユーザーが触れるのは名前空間側の束縛操作と、オブジェクト側のメソッド呼び出しのみ。両者の境界は密閉されている。

## 2つの空間

```
┌─────────────────────┐         ┌──────────────────────┐
│   名前空間           │         │   オブジェクト空間    │
│  (namespace)        │         │   (object space)     │
│                     │         │                      │
│  x ────────────────────────►  [ int: 121 ]          │
│  original ─────────────────►  (同じオブジェクト)    │
│  rev ──────────────────────►  [ int: 0 ]            │
│                     │         │                      │
│  グローバル/局所     │         │  全部 heap 上、       │
│  などのスコープ      │         │  GC で管理            │
└─────────────────────┘         └──────────────────────┘
```

- **名前空間**: 実装としては `dict`（`globals()`, `locals()` が dict を返す）。「名前 → オブジェクトへの束縛」を保持。スコープごとに階層構造を持つ。
- **オブジェクト空間**: 値そのものの世界。各オブジェクトは生存期間中不変の identity を持つ。型・値・メソッドを担う。

## 言語の操作はどの空間に作用するか

| 操作           | 作用先                                            |
| ------------ | ---------------------------------------------- |
| `x = expr`   | **名前空間**: 名前 `x` を式の評価結果（オブジェクト空間の要素）に束縛し直す    |
| `x` を式で参照    | **両空間をまたぐ**: 名前空間で `x` を引いて、得られたオブジェクトを返す      |
| `x.attr = v` | **オブジェクト空間**: `x` が指すオブジェクトの状態を変更（mutable な場合） |
| `del x`      | **名前空間**: 束縛を削除（他から参照があればオブジェクトは生存）            |
| `id(x)`      | オブジェクトの identity を返す。**名前のアドレスではない**           |
| `is`         | 2つの式が **同じオブジェクト** を指しているか                     |
| `==`         | `__eq__` を呼び、値として等しいか                          |

## immutable / mutable の再解釈

- **immutable** (int, str, tuple, frozenset): オブジェクト空間で **状態が変わらない**。「変更したように見える操作」(`x += 1`) は必ず **名前空間側の再束縛** として実現される。よって複数の名前が同じオブジェクトを指していても、片方の再束縛は他方に影響しない。
- **mutable** (list, dict, set): オブジェクト空間で **同じ identity のまま中身が変わる**。複数の名前が同じオブジェクトを指していると、片方経由の変更が他方からも見える（エイリアシング）。

```py
# immutable: original は影響を受けない
original, x = 121, 121
x //= 10        # x が別の int オブジェクトに付け替えられるだけ
# original == 121

# mutable: 両方変わる
original, lst = [1,2,3], [1,2,3]
lst = original
lst.append(4)   # オブジェクト空間に作用
# original == [1,2,3,4]
```

## 関数呼び出しもこのモデルで一貫

「Python は call by value か reference か」という議論はこのモデルで解決する。

- 仮引数も **名前**。
- 関数呼び出し時、仮引数という名前を呼び出し側のオブジェクトに束縛する（= 関数の名前空間に新しい束縛が作られる）。
- 関数内で `param = ...` しても呼び出し側の名前空間は影響を受けない（別の名前空間だから）。
- 関数内で `param.append(...)` するとオブジェクト空間に作用するので、呼び出し側からも変わる。

これは **call by object reference / call by sharing** (Liskov の用語) と呼ばれる。

## 実践: 関数にリストを渡すとき

### `return` するかどうかは無関係

**引数は一切コピーされない**。仮引数は呼び出し側と同じオブジェクトに束縛されるだけなので、`return` の有無で挙動は変わらない。判断基準は「その操作がオブジェクト空間に作用するか、名前空間に作用するか」の一点。

```py
def f_mutate(xs):
    xs.append(99)     # オブジェクト空間に作用
    return xs         # return しても関係ない

def f_rebind(xs):
    xs = xs + [99]    # 新しいリストを作り、局所名 xs を付け替え
    return xs

original = [1, 2]
f_mutate(original)    # original == [1, 2, 99]  ← 汚染される
original = [1, 2]
f_rebind(original)    # original == [1, 2]      ← 無傷
```

`f_rebind` が安全なのは「引数が複製されたから」ではなく、**`xs + [99]` が新しいオブジェクトを作り、名前空間側の再束縛で終わっているから**。

### mutable / immutable ではなく「再束縛か、ミューテートか」

mutable なオブジェクトでも、再束縛なら呼び出し側に伝わらない。immutable / mutable という軸より、操作がどちらの空間に作用するかで見る方が正確。

| 操作 | 作用先 | 呼び出し元に見えるか |
|---|---|---|
| `n = n + 1` / `xs = xs + [9]` | 名前空間（再束縛） | 見えない |
| `xs = sorted(xs)` | 名前空間（新オブジェクト） | 見えない |
| `xs.append(9)` / `xs[0] = 9` / `xs.sort()` | オブジェクト空間 | 見える |

Python は破壊的メソッドと新オブジェクトを返す関数を意図的にペアで用意している（`sort()` / `sorted()`、`reverse()` / `reversed()`）。この対応を覚えておけば都度考えなくて済む。

### `+=` は型によって作用先が変わる

```py
n = 1
n += 1        # int には __iadd__ が無い → n = n + 1 に落ちる → 再束縛

xs = [1]
xs += [9]     # list.__iadd__ は extend → in-place ミューテート
```

`+=` は「拡張代入」であって、常に再束縛とは限らない。`__iadd__` を持つ型では**同じ identity のまま中身が書き換わる**ため、呼び出し側に伝わる。「`+=` だから安全」という一般則は成り立たない。

### 影響させたくない場合

明示的にコピーを取る。

```py
copied = xs[:]        # スライス
copied = list(xs)     # コンストラクタ
copied = xs.copy()    # メソッド
```

いずれも**浅いコピー**なので、2次元リストでは内側の行オブジェクトが共有されたままになる。

```py
grid = [[1, 1], [0, 0]]
copied = list(grid)   # 外側のリストだけ複製、行は元と同じオブジェクト
copied[0][0] = 9      # grid も [[9, 1], [0, 0]] になる
```

深くコピーするなら:

```py
copied = [row[:] for row in grid]   # 2次元ならこれで十分
import copy
copied = copy.deepcopy(grid)        # 任意の入れ子
```

なお、グリッド探索で `visited` を使わず訪問済みマスを `grid[x][y] = WATER` と書き換える定番テクニックは、**呼び出し元の入力を破壊している**。競技/LeetCode では許容されるが、実務では「入力を破壊する関数」なので、ドキュメント化するかコピーを取るかの判断が要る。面接でこの解法を出すときは「入力を書き換えてよいか」を一言確認するとよい。

## C++ ポインタとの違い

| C++ | Python |
|---|---|
| 変数 = メモリ上の領域 (lvalue) | 名前 = 名前空間内の束縛 |
| 値はその領域に直接置かれる (or ポインタ経由) | 値は常にオブジェクト空間にあり、名前は参照を保持 |
| `int x = 5; x = 6;` は領域を上書き | `x = 5; x = 6` は名前を別の int オブジェクトに付け替え（5 は他に参照がなくなれば GC） |
| `&x` でアドレスが取れる | 名前のアドレスは取れない（境界が密閉） |
| ポインタ算術 (`p+1`) ができる | 名前に対する算術はない |
| ダブルポインタ `T**` がある | 名前を値として持ち出せない |

Pythonの名前は「自動でデリファレンスされ、アドレス取得も算術もできないポインタのように振る舞う」が、言語仕様上はポインタでも参照でもなく **名前束縛という別物**。

## id() について補足

`id(x)` はオブジェクトの **identity** を表す整数を返すと定義されているだけで、言語仕様はメモリアドレスと結びつけていない。
- CPython では実装上たまたまアドレスを返している
- PyPy のような moving GC ではオブジェクトが移動するため、`id()` はアドレスそのものではない

つまり identity は **オブジェクト空間の内的属性** であり、メモリレイアウト（実装空間）とは別レイヤ。
